# Recovery Protocol (Протокол восстановления после сбоев)

Данный документ описывает механизмы обеспечения отказоустойчивости (fault tolerance) и восстановления состояния агента после различных типов сбоев. Это критически важный компонент архитектуры «бессмертия», гарантирующий непрерывность идентичности агента даже при аварийных ситуациях.

> *Примечание: все биологические аналогии используются исключительно как концептуальные метафоры.*

## Жизненный цикл восстановления

Базовый сценарий восстановления после отказа вычислительного узла:

Agent A (ACTIVE)
  ↓ [Checkpoint]
Storage (HIBERNATION)
  ↓ [Node Failure]
Node B (RESTORE)
  ↓ [Validation]
Agent A' (ACTIVE) — идентичность сохранена

## Ответы на критические вопросы восстановления

### 1. Авария во время записи checkpoint
**Проблема:** Если узел падает в момент сериализации состояния, файл checkpoint может быть повреждён.
**Решение:** Использовать атомарную запись. Сначала состояние записывается во временный файл (checkpoint.tmp), а после проверки переименовывается в финальный. Если авария произошла во время записи — предыдущая версия остаётся целой.

### 2. Повреждение записи
**Проблема:** Файл checkpoint существует, но его содержимое повреждено.
**Решение:** Многоуровневая проверка целостности. Каждый файл сохраняется с контрольной суммой (SHA-256). При восстановлении хэш пересчитывается. Если файл битый — система берёт предыдущую сохранённую версию.

### 3. Определение последней корректной версии
**Проблема:** Как система понимает, какой checkpoint использовать?
**Решение:** Механизм «указателя». Отдельный маленький файл latest_checkpoint.json хранит ссылку на последнюю подтверждённую версию. При восстановлении система читает именно его.

### 4. Предотвращение двух одновременно работающих копий
**Проблема:** Возникают две копии одной личности.
**Решение:** Механизм «аренды» (lease). Агент получает лицензию на работу на 60 секунд и должен регулярно продлевать её (heartbeat). Если узел упал — лицензия истекает, и другой узел может законно восстановить агента.

### 5. Решение проблемы split-brain
**Проблема:** Два узла одновременно считают себя главными.
**Решение:** Консенсус через распределённую блокировку (distributed lock). Только узел, получивший внешнюю блокировку, может запустить агента.

### 6. Синхронизация памяти
**Проблема:** Новые воспоминания не успели сохраниться в общее хранилище.
**Решение:** Двухуровневое сохранение. Рабочая память пишется в checkpoint, а долговременная память сразу уходит в векторную базу данных (append-only). При восстановлении узел подтягивает всё, что появилось после последнего checkpoint.

### 7. Проверка целостности состояния
**Проблема:** Как убедиться, что восстановленное состояние корректно?
**Решение:** Многоэтапная валидация: проверка структуры (JSON Schema), проверка хэша и тестовый прогон (self-test). Если не проходит — откат к предыдущей версии.

### 8. Частичная потеря данных
**Проблема:** Некоторые компоненты состояния восстановлены, другие нет.
**Решение:** Компонентное восстановление. Каждый из 8 компонентов личности (см. identity-state.md) сохраняется независимо. Если один битый — берём его старую версию, остальные оставляем новыми.

### 9. Откат ошибочного обучения
**Проблема:** Агент запомнил что-то неправильное.
**Решение:** Механизм отката (rollback) с версионностью. Все изменения в памяти логируются. Пользователь может дать команду откатить память к состоянию на вчерашний день.

## Сценарии аварий

**Сценарий A: Плановая гибернация**
Агент сохраняет checkpoint, обновляет указатель версии и переходит в статус STORAGE. Ресурсы освобождаются.

**Сценарий B: Внезапный отказ узла**
Система мониторинга видит, что heartbeat пропал. Координатор снимает блокировку с упавшего узла. Новый узел захватывает блокировку, читает указатель версии, загружает последний checkpoint и запускает агента.

**Сценарий C: Повреждение checkpoint**
При восстановлении хэш не совпадает. Система автоматически пытается загрузить версию v-1, затем v-2. Если все битые — генерируется критический alert.

## Метрики надёжности
- **RTO (Recovery Time Objective):** время восстановления (цель: <30 сек).
- **RPO (Recovery Point Objective):** максимальная потеря данных (цель: <1 минуты работы).

> *Примечание: данный протокол является базовой спецификацией (v1) и будет расширяться по мере развития архитектуры.*
